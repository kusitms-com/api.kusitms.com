# Code Review Convention

코드 리뷰는 변경 사항이 요구사항을 충족하는지 검증하고, 구현 의도와 개선 방향을 공유하기 위한 협업 과정이다.

## 1. PR 작성 및 리뷰 요청

- 하나의 PR은 하나의 이슈 또는 명확한 작업 목적을 중심으로 작성한다.
- 관련 없는 기능 변경과 리팩토링을 한 PR에 혼합하지 않는다.
- PR 템플릿에 따라 작업 배경, 변경 사항, 완료 조건, 테스트 결과를 기록한다.
- 테스트를 수행하지 못했다면 미검증 범위와 사유를 작성한다.
- API, DB, 설정 변경이 있다면 영향 범위와 관련 문서 변경 사항을 명시한다.
- 리뷰 요청 전에 작성자가 변경 사항을 직접 확인한다.

## 2. 코드 리뷰 기준

| 검토 영역 | 확인 사항 |
| --- | --- |
| 기능 및 요구사항 | 완료 조건 충족, 정상·예외 흐름, 기존 기능 영향 |
| 코드 품질 | 네이밍·디렉토리 컨벤션, 책임 분리, 중복 코드, 가독성 |
| 데이터 및 안정성 | 트랜잭션, 데이터 정합성, 동시·중복 요청, 예외 처리 |
| 보안 | 인증·인가, 입력 검증, 민감 정보 노출 여부 |
| 테스트 | 테스트 범위, 검증 방법과 결과, 미검증 항목 |
| 문서 및 운영 | API 명세, DB·환경 설정 변경, 배포 영향 |

## 3. 리뷰 코멘트 규칙

- 작성자가 아닌 코드와 구현 방식에 집중한다.
- 수정이 필요한 이유와 예상되는 영향을 구체적으로 설명한다.
- 가능한 경우 대안이나 개선 방향을 함께 제시한다.
- 필수 수정과 선택적 제안을 구분한다.

| 접두사 | 의미 | 처리 기준 |
| --- | --- | --- |
| `[MUST]` | 기능 오류, 보안, 데이터 정합성 등 필수 수정 | 수정하거나 논의 후 해결해야 승인 가능 |
| `[SUGGEST]` | 구조·가독성·유지보수성 개선 제안 | 논의 후 반영 여부 결정 |
| `[QUESTION]` | 구현 의도나 설계 판단에 관한 질문 | 설명 또는 논의 |
| `[NIT]` | 사소한 표현·스타일 의견 | 선택적 반영 |

### 코멘트 예시

> [MUST] 중복 요청 시 동일한 데이터가 두 번 생성될 수 있습니다. DB 제약 조건 또는 중복 요청 방어 로직을 확인해 주세요.

> [SUGGEST] 이 로직을 별도 메서드로 분리하면 흐름을 이해하기 쉬울 것 같습니다.

> [QUESTION] 이 예외를 서비스에서 처리한 이유가 있을까요?

> [NIT] 변수명을 조금 더 구체적으로 작성하면 의미가 명확할 것 같습니다.

## 4. 리뷰 반영 및 재검토

### PR 작성자

- 리뷰 의견에 수정 내용 또는 미반영 사유를 답변한다.
- 주요 로직 변경 시 관련 테스트를 다시 수행하고 결과를 갱신한다.
- 논의가 필요한 의견은 임의로 종료하지 않는다.

### 리뷰어

- 변경된 코드가 리뷰 의견을 해결했는지 확인한다.
- 추가 수정으로 발생할 수 있는 영향을 확인한다.
- 논의가 완료된 코멘트는 해결 상태로 정리한다.

## 5. 승인 및 병합 기준

- 작업 목적과 완료 조건을 충족해야 한다.
- `[MUST]` 의견이 모두 해결되어야 한다.
- 필요한 테스트 결과와 미검증 항목을 확인해야 한다.
- 관련 문서와 설정 변경이 반영되어야 한다.
- 최소 한 명 이상의 리뷰어 승인을 받아야 한다.
- 필수 CI 검사가 통과해야 한다.
- `main` 브랜치에 직접 커밋하지 않고 PR을 통해 병합한다.
- PR 작성자는 자신의 PR을 단독으로 승인하지 않는다.

## 6. 긴급 변경 예외

긴급 장애 대응 등 일반적인 리뷰 절차를 따르기 어려운 경우 팀 내 합의로 예외를 적용할 수 있다. 이 경우에도 변경 사유, 테스트 결과와 남은 위험을 기록하고 병합 이후 필요한 리뷰를 진행한다.
